What the dataset actually contains, what signals the labelling uses, and what the
rest of the team needs to know. Everything below is measured from
`backend/data_prep/out/dataset.csv`, regenerable with `python backend/data_prep/build_dataset.py`.

## 2. Key signals — what actually separates these entries

### 2a. Attachment presence is near-perfectly predictive

| | has attachments | no attachments |
|---|---|---|
| BL_COMPARISON | 126 | 3 |
| Everything else | 0 | 391 |

Every email with an attachment is a comparison request — **100% precision**. The
3 exceptions are `email_506/508/510`, which say outright that the attachments were
dropped in transit.

This is the single strongest feature in the dataset, and **BERT cannot use it**,
because BERT only sees subject + body. Worth wiring into the production pipeline
as a rule regardless of what the model says.

### 2b. Bodies come from ~20 fixed templates

The inbox is synthetic. Twenty regexes (`build_dataset.py:RULES`) classify all 520
emails with zero fallbacks — `test_pipeline.py` fails if even one email falls
through. Representative sentences:

| Signal phrase | Category |
|---|---|
| "Attached are the SI and draft BL…" / "check the draft BL against the SI" | BL_COMPARISON |
| "Please find Shipping instruction for…" | SI_REQUEST |
| "Please assist to send the draft BL for X for checking asap" | SI_REQUEST *(judgement call — see §3)* |
| "GR is still missing" / "THC / local charge" / "D&D / detention charges" | INVOICE_QUERY |
| "automated notification" / "berthing report" / "list of outstanding BL" | GENERAL |
| "monthly draw" / "unpaid customs fee" / "urgent business proposal" | SPAM |

### 2c. Subjects are deliberately misleading — classify on the body

The official brief lists "misleading email subjects" as an intentional difficulty,
and the data confirms it. `email_003` has the subject
`RE_ TO CONFIRM DOCS _ 5AAT-03056 … SIN525534192` — which reads like a comparison
thread — while the body asks about a *different* booking, `SIN832764835`.

Subject shapes are shared across categories, so they carry no separating signal.
All classification is done on the body.

### 2d. The same field is labelled 64 different ways

This is the core extraction problem, and the reason naive string matching fails:

| Field | Spellings | Examples |
|---|---|---|
| gross_weight_kg | 12 | `GROSS WEIGHT`, `Gross Wt (kgs)`, `Gross Weight毛重(KGS)`, `TOTAL Gross Wt (kgs)` |
| port_of_discharge | 10 | `POD`, `Discharge Port`, `Port of Discharge (POD)`, `Port of Discharge (卸货港)` |
| shipper | 9 | `Shipper`, `SHIPPER`, `Shipper/Exporter`, `Shipper (Principal or Seller)`, `Exporter` |
| port_of_loading | 9 | `POL`, `Load Port`, `Port of Loading (POL)`, `PORT OF LOADING (装货港)` |
| consignee | 8 | `Consignee`, `CONSIGNEE`, `To the Order of`, `Consignee (Non-Negotiable)` |
| notify_party | 8 | `Notify`, `NOTIFY PARTY`, `Notify Party/Intermediate Consignee` |
| container_count | 8 | `No. of Containers`, `Container Count`, `Total Containers`, `No. of Containers or Packages` |

Some documents carry bilingual CJK glosses (`发货人`, `箱数`, `毛重`). `fields.py`
strips CJK and parentheticals, then matches a cleaned label against 7 ordered
patterns. `NOTIFY` must be tested before `CONSIGNEE`, or
`Notify Party/Intermediate Consignee` lands on the wrong field.

### 2e. Values are drawn from small closed vocabularies

| Field | Distinct values across all 250 attachments |
|---|---|
| shipper | 3 |
| port_of_loading | 7 |
| container_count | 13 |
| consignee / notify_party | 20 each |
| port_of_discharge | 26 |
| gross_weight_kg | 135 |

Because the vocabularies are this small and this clean, **exact match after
normalisation was sufficient** — zero of the 64 `OK` pairs needed fuzzy matching
to pass. Fuzzy comparison is retained in `fields.py:same()` as a hedge for live
email, but it is doing nothing on this corpus. That also means no false negatives
are hiding behind a similarity threshold.

### 2f. Four layouts, one scanner

```
.txt        "Port of Loading (POL): SINGAPORE"
.xlsx       "Port of Loading (POL) | SINGAPORE"
.pdf/.docx  "PORT OF LOADING"  ← label alone, value on the following line(s)
```

One line-scanner handles all three shapes. Two layout traps:

- PDF bills of lading repeat `GROSS WEIGHT (KG)` as a per-container table header
  before stating the total, so the parser takes the **last** numeric match, not the first.
- Party fields keep only the **first line** of the value. Keeping the address block
  would make `EAST BRIGHT FZ-LLC` and `UAB NOVAKOPA` look ~90% similar — they share
  an address — and a real defect would be silently swallowed.

### 2g. Blank placeholders are not mismatches

`____MT`, `_______ MTS`, `???`, `TBA`, `N/A` mean *the customer left this blank*.
Treated as missing (→ `NEEDS_REVIEW / missing_value`), never as a differing value.
Getting this wrong turns 5 review cases into 5 false alarms.

## 3. Three judgement calls

These are decisions, not facts. Each is reversible in one line of `RULES`.

| # | Case | Rows | Decision | Why |
|---|---|---|---|---|
| 1 | "Please assist to send the draft BL for X for checking asap", no attachment | **91** | `SI_REQUEST` | The brief says only comparison requests continue to the checking step; these have nothing to check. |
| 2 | "Reminder: please submit SI & AED for all pending shipments" | 21 | `GENERAL` | A bulk reminder, not a shipment-specific request. |
| 3 | `email_512/513/514` — legible image-only scans | 3 | `NEEDS_REVIEW / unreadable` | Not worth an OCR path for 3 of 520. The brief's reliability axis asks for exactly this. |

**#1 is the one that matters** — 17% of the corpus, and it swings macro-F1 more
than anything else. All 91 are a single template varying only by greeting name and
booking reference, so they move together. If the self-evaluation endpoint
disagrees, this is the line to flip.

## 4. Validation status — read before quoting any number

The 20 planted edge cases (`email_501`–`520`) land **exactly 5/5/5/5** across
`wrong_doc_type` / `missing_attachment` / `unreadable` / `missing_value`. That
symmetry is the strongest evidence the comparison logic is correct.

All 45 mismatches were inspected by hand: **no false positives**.

What has **not** happened: nobody has hand-checked a random sample against the
source documents. `backend/data_prep/out/holdout/` holds 20 raw unlabelled emails plus
their attachments for exactly that. The rules' answers are sealed in
`test.csv` — write your own labels first, then diff.

## 5. Handoff — one line per finding

**For the BERT teammate**

1. Use `train.csv`, columns `bert_text` → `label_id` (0=BL_COMPARISON, 1=SI_REQUEST, 2=INVOICE_QUERY, 3=GENERAL, 4=SPAM). Holdout rows are not in this file.
2. Class balance is 5.4:1 — use class weights, early-stop on **macro-F1**, not accuracy.
3. Max input is 1,293 chars, so 512 tokens truncates nothing. No preprocessing needed.
4. **Your validation accuracy will be inflated and should not go in the demo.** 520 emails contain only 177 distinct patterns, and 15 rows are byte-identical. The model is memorising templates, which is fine for a demo but is not evidence the system generalises.
5. 37% of bodies carry a quoted reply chain whose text is always the same filler ("Please follow the previous instruction"). It adds length, not signal. Stripping it is optional.

**For whoever builds the pipeline**

6. Attachment presence predicts `BL_COMPARISON` with 100% precision — encode it as a rule, don't rely on the model to learn it.
7. Classify on the **body**. Subjects are deliberately misleading and are shared across categories.
8. Reuse `extract.py` and `fields.py` directly — they already handle all four formats, 64 label spellings, CJK glosses, and the PDF table trap.
9. Blank placeholders (`____`, `TBA`, `N/A`) must route to `missing_value`, never to a mismatch.
10. `submission.json` is valid and ready for `POST /submit` right now. That endpoint is the only external check on judgement call #1 — run it early.

**For whoever writes the deck**

11. Headline numbers: 520 emails classified, 45 genuine document defects caught, 20 escalated to human review with a specific reason attached.
12. The honest framing is *precision* — no false alarms across 45 mismatches — not model accuracy.

## 6. The fine-tuned BERT — as trained, 21 Sep 2026

Merged from `feature/finetuned-bert` (`baa7346`). Source of every number below:
the saved cell outputs in `backend/model/finetuned_bert.ipynb`.

### Training setup

| | |
|---|---|
| Base model | `bert-base-uncased` |
| Input | `subject + "
" + body`, truncated at 512 tokens (nothing truncates — see §1) |
| Labels | the 5 SDOC classes, order frozen to match `build_dataset.py` |
| Split | `train.csv` 500 rows → 400 fit / 100 validation (stratified, seed 42); `test.csv` 20 rows held out |
| Schedule | 5 epochs, lr 2e-5, batch 8, weight decay 0.01, fp16 |
| Checkpoint | best by **macro-F1**, evaluated every epoch — the §5 item-2 advice was followed |
| Hardware | Colab **GPU**, ~3 min wall clock for the run |

### Results

Validation, per epoch (accuracy / macro-F1):

```
epoch 1   0.650  0.533
epoch 2   0.980  0.959
epoch 3   1.000  1.000
epoch 4   1.000  1.000
epoch 5   1.000  1.000
```

Held-out test (20 rows, run once): **accuracy 1.000, macro-F1 1.000**, loss 0.158.
Inference confidences on the 20 holdout emails run 0.65–0.97, lowest on SPAM.

### What the number does and does not prove

§5 item 4 still stands and is now measurable: the ceiling was hit at **epoch 3**,
on a corpus of 177 distinct templates with 13 duplicate `bert_text` rows in
`train.csv`, and 2 of the 20 test texts also appear in train after normalisation.
A perfect score here means *the templates were learned*, not that the model
generalises to a live inbox. Quote it as corpus performance, and keep
attachment-presence (§2a) as a rule — the model cannot see attachments at all.

### Serving

The model is wired into the API, not just the notebook:

- `POST /api/v1/classification` → `{category, confidence, scores{5}, device}`
  (`app/api/routes/classification.py`)
- `app/services/email_classifier.py` loads weights **once** behind a lock, reuses
  them for every request, picks CUDA when available and falls back to CPU, and
  raises `503 ModelUnavailableError` rather than crashing when the model
  directory is absent.
- Weights are **not** in the repo. Point `DOCUVERIFY_MODEL_DIR` at a local copy;
  the default is `backend/model/email_multiclass_classifier`.
